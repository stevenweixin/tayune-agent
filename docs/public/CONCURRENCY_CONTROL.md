# TAYUNE-Agent：分层并发控制

更新时间：2026-11-04。正式代码已替换全局单请求锁，并新增有界短等待、会话容量配置及分类分道。
本次未重启8011生产进程，代码同步不等于部署。

## 目标与本轮范围

目标是面向C端的并发服务：不同用户的网络等待可以重叠，同一会话和稀缺推理资源分别保护。
本机阶段先采用单进程、有界准入与CPU排队，不通过无限排队、无限线程或取消预算换取表面吞吐。
这不是分布式高并发平台已经完成的声明。

## 原问题

旧Service用一个全局执行锁覆盖分类、检索、模型网络等待和会话保存。
任意用户正在回答时，其他用户立即429，空闲CPU也无法接收新的分类任务。
单独移除该锁又会触发CPUWorker忙时拒绝；前一轮真实依赖实验中8次请求有6次降级。

## 正式实现

| 层级 | 当前行为 | 保护什么 |
| --- | --- | --- |
| 聊天/任务恢复准入 | 默认4个执行，最多16个等待，最多等2秒，队满或超时429 | 供应商调用及有界在途工作量 |
| 同会话所有权 | 聊天、恢复、记忆修改和删除共用会话占用检查 | 防止旧历史快照覆盖新状态 |
| 分类队列 | 最多32个待处理，排队加执行5秒，一次一个分类 | 避免短分类排在长Rerank后 |
| RAG队列 | 最多16个待处理，排队加执行35秒，一次一个 | Embedding、检索/精排共享资源 |
| 知识工具 | 正式Runtime按聊天容量的2倍设待处理上限，默认8，内部串行 | 不把多路知识请求无限堆积 |
| 工具网关 | 继续最多2路工具执行，详情依赖已查到的商品ID | 外部读取及业务依赖 |
| 数据库 | 请求登记、日计数保持同一SQLite事务，幂等约束不变 | 防止重复登记、重复扣次 |
| 会话存储 | Runtime默认最多5000个有效会话；普通get只读，过期访问立即删除 | 去除100会话硬编码与逐次全局清理 |

`RequestCoordinator`在同一事件循环中完成无await的检查和登记；读取会话历史之前先占用所有者。
它是单进程控制器，不是跨进程锁。网络调用等待期间，其他会话仍可使用剩余执行名额。

排队期间保留同会话保护，但不登记任务、不扣日次数、不调用模型。执行名额FIFO移交；
等待取消/超时会移除等待者，刚拿到名额就取消时归还名额。
聊天拿到名额后重新检查会话；任务恢复还会重新检查60秒证据有效期及版本。
4个执行加16个等待不是20路推理，更不意味着3000人都能得到回答。

正常重放已保存的幂等结果不占新的聊天执行名额、不再次调用模型；同会话仍有在途任务时，
重复提交立即拒绝，不启动第二份计算。证据版本及60秒有效期检查照旧。

记忆修改只拒绝自身会话繁忙，不再因为其他顾客正在聊天就阻止修改。管理路由的本机限制及Bearer所有权检查未放宽。
取消必须属于该会话，且不会取消其他人的任务；取消后要等子任务退出才释放会话名额。
恢复任务不能绕过容量或同会话保护；主动取消恢复任务时返回正常的取消结果，HTTP调用者自身取消则继续传播取消。

CPUQueue保留底层CPUWorker：协程取消/超时不代表工作线程停止。
同一通道的后续CPU请求必须等待残留线程真正结束；排队中已取消的请求不会在稍后偷偷开始执行。
队列关闭后拒绝新工作。CPU日志只包含任务ID、阶段、排队和执行等待耗时，不记录问题、参数或会话Token。

## 配置与部署

```dotenv
TAYUNE_MAX_CONCURRENT_CHATS=4
TAYUNE_MAX_WAITING_CHATS=16
TAYUNE_ADMISSION_WAIT_SECONDS=2
TAYUNE_MAX_SESSIONS=5000
```

执行容量校验1–32，等待数量0–128，等待期限0.01–5秒，会话上限1–100000。
这些上界不是性能验收值。等待数量设0恢复立即拒绝；默认执行仍4，没有直接调到3000。
Runtime读取配置并传给SessionStore/Service；修改后需要重启应用生效。
基础SessionStore直接构造仍兼容旧默认100，TeaService直接构造兼容不等待；正式入口显式传Runtime配置，
不能用旧fixture的默认构造来推断当前线上设置。
没有修改真实`.env`、模型名、日额度、IP限频或8秒会话间隔。

本轮没有改插件、Tunnel、Milvus数据或课堂环境，没有进行付费问答。
当前8011进程没有被自动重启，所以不能说线上已加载新容量底座。

SQLite启用WAL，增加过期及轨迹查询索引，不降低synchronous持久性设置。
全局清理默认最多每60秒一次，读取过期令牌仍立即失效并清除其私有记录。
WAL仍只有一个写者，也不适用于跨机器网络共享文件系统；参见[SQLite说明](https://www.sqlite.org/wal.html)。
服务仍有同步SQLite提交，不能声称已经消除全部事件循环阻塞。活动数据库备份应使用SQLite backup API，
不要只复制主文件而遗漏未合并的WAL；本轮未打开或迁移生产数据库。

仍须单进程启动。SQLite任务启动恢复逻辑和进程内所有权尚未适配多worker；不能直接把Uvicorn worker增加后共享同一数据库。

## 面试口述

“我的目标是C端并发服务，不是所有用户共用一把大锁。现在正式实现允许不同会话有限并发，
同一会话保持串行，CPU推理单独有界排队。网络等待可以重叠，CPU不会无限叠加。
本机默认4路只是当前资源保护配置，并不是系统的永久上限；更高容量需要真实混合负载验证。
