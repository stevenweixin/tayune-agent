# 容量改造第一阶段：会话、短等待与推理分道

日期：2026-11-04。改造前基线`02dda57`。本阶段已修改正式代码并完成隔离验证，未重启或部署到生产。
目标是为容量扩展建立可靠底座，不宣称完成3000真实用户的高并发服务。

## 1. 为什么先做这些

[上一轮测试](SCALE_QUALITY_EVALUATION_20261104_ZH.md)暴露了100会话硬上限、大量拒绝和集中突发建连超时。
代码检查还确认：每次读取会话都会触发全局过期清理，繁忙拒绝也要扫描/提交多张表；
短分类与长检索精排共享串行CPU队列，会出现队头阻塞。

因此本轮不是取消所有保护或只把4改成3000，而是减少热路径工作、吸收有限短突发、分开调度不同模型。
模型提示词、检索内容、证据规则与商品推荐逻辑没有修改，上一轮回答质量问题仍然存在。

## 2. 已实现

| 改动 | 当前行为 | 保护与限制 |
| --- | --- | --- |
| 会话容量 | Runtime默认5000个未过期会话，可配置 | 会话数不是同时执行数；基础Store直接构造保留旧默认100 |
| 注册事务 | 同一条INSERT SELECT完成有效会话计数与创建 | 不用预置数据冒充注册；仍不支持多实例业务协调 |
| 读取热路径 | 普通get只进行主键查询和反序列化 | 不再为每个拒绝/读取请求全局清理和commit |
| 过期处理 | 全局最多每60秒清理一次，访问过期会话立即删除私有记录 | 不因清理节流延长24小时令牌有效期；已过期行不占有效会话额度 |
| SQLite | WAL、过期/所有者/审计查询索引 | 保留FULL持久性；仍单写者、同步提交、单进程 |
| 请求准入 | 默认4个执行，最多16个FIFO等待者，最多等2秒 | 队满/超时429；排队不登记任务、不扣次、不调用模型 |
| 同会话 | 等待和执行期间均保持所有权 | 不能同时改记忆、恢复或再次提交同一会话 |
| CPU调度 | 分类单独32待处理/5秒；RAG16待处理/35秒；各自串行 | 避免调度上的队头阻塞，不是物理CPU独占或吞吐翻倍 |
| 取消/恢复 | 取消移除等待者或归还已移交名额；恢复排队后重新核验证据版本/60秒时效 | 不在短等待后使用过期价格或检查点 |
| 客户端提示 | 容量拒绝附Retry-After:2 | 是退避提示，不保证两秒后一定有名额，不自动重试计费 |

实现分别位于`app/database/session.py`、`runs.py`、`app/core/concurrency.py`、`cpu_worker.py`、
`runtime.py`、`app/agent/service.py`及`app/main.py`。
没有引入新第三方运行库、付费服务或容器，也没有修改课堂环境/Milvus。

## 3. 默认配置及生效边界

```dotenv
TAYUNE_MAX_SESSIONS=5000
TAYUNE_MAX_CONCURRENT_CHATS=4
TAYUNE_MAX_WAITING_CHATS=16
TAYUNE_ADMISSION_WAIT_SECONDS=2
```

配置示例已更新，真实`.env`未改。若环境已有显式值，以环境值为准；新代码只在重新启动后生效。
执行1–32、等待0–128、等待时限0.01–5秒、会话1–100000是输入保护范围，不是已验证容量。
等待数设0可以关闭短等待，保留旧的立即拒绝方式；日额度、IP限制、8秒会话间隔与每问预算不变。
这两秒仅是应用准入等待，不是网络建连或整个HTTP请求的总时限。原85秒执行期限保持不变。

仍须单进程启动。RunStore启动恢复、进程内所有权和计数没有分布式租约，不能直接增加Uvicorn workers。
SQLite WAL改善读写互扰，但不提供多写者或跨机器数据库；不能放到网络共享文件系统上当集群存储。
备份活动数据库应使用SQLite backup API，不能只拷贝主文件忽略WAL。
本轮未打开生产会话数据库执行迁移；添加索引和WAL切换只在隔离数据库验证。

## 5. 3000虚拟用户复测

测试使用正式注册入口创建3000个会话，3000/3000成功、0次预置，约2.153秒完成注册阶段。
这仅验证本机存储及入口路径；测试实例提高IP/日限制，不能当作公网注册吞吐。

所有模型、检索、商品仍为固定依赖；模型每次固定等待0.25秒、商品0.05秒，
分类与精排分别模拟约0.02/0.2秒。Locust独立进程但与后端同机，backlog4096。
与前一轮的单次结果并列观察，不能当作严谨拆分变量实验或真实供应商改善百分比。

| 场景 | 改造前观察 | 本轮观察 |
| --- | --- | --- |
| 正式3000次注册 | 100成功、2900次429 | 3000成功，不预置 |
| 3000用户渐进负载 | 6079提交，275完成，5804次429 | 6069提交，363完成，5706次429 |
| 渐进负载完成请求P95 | 1.090秒 | 2.772秒 |
| 集中3000次提问 | 10完成、2730次429、260次建连超时 | 20完成、2980次429、0次建连超时 |
| 集中突发完成请求P95 | 8.148秒 | 4.965秒 |

本轮无5xx和降级，但仍有约94%的渐进请求被限流；集中突发只有20条完成。
短队列减少立即拒绝、也增加部分成功请求的等待，所以不能宣称所有延迟都下降。
渐进阶段实际事件窗口约62.70秒，包含爬升及收尾，并非60秒满负载稳态。
集中请求开始跨度约0.527秒；目标25秒，停止等待中的虚拟用户使事件窗口约60秒，不能称持续60秒3000请求并发。

本轮没有复现连接超时，但两次同机短测不足以证明根因已排除或所有网络条件下都解决。
发压端仍约100.3%、后端98.6%的进程CPU，占用接近各自一个核；下一阶段应异机/多worker复核。

最终391个任务完成（日计数391），包含8个控制问答、363个渐进和20个突发；782次模拟模型调用，
等待超时163次，队满等立即拒绝8523次，合计8686个未完成聊天请求。
active=0、waiting=0、owner=0，等待峰值16，未观察到名额或扣次泄漏。
本轮0付费模型调用，不发布新的回答准确率或真实LLM吞吐结论。

## 6. 尚未完成的容量工作

1. **共享状态**：会话、任务、幂等及限额从单机SQLite迁移到经过验证的共享存储。
2. **跨实例协调**：会话执行租约、取消/恢复归属、启动恢复逻辑，防止多个实例接管同一任务。
3. **推理服务拆分**：独立部署或经过测试的CPU/GPU工作池，而不是为每个API实例复制全部重模型。
4. **真实混合负载**：异机持续压测、供应商配额和费用上限、排队截止时间与质量对照。
5. **可观测性**：脱敏外部工具状态、排队分布、事件循环/数据库提交等待、网络连接与拒绝原因。

因此本阶段只能说“去掉100会话硬编码、减少清理风暴并加入可靠背压”，
不能说“已经能服务3000个同时提问的真实用户”。既有回答质量问题仍待独立修复。
