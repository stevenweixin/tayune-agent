# 修复日志

## 2026-10-20：长片段导致知识工具精排失败

状态：正式代码已修复，通过离线回归及本机 Milvus / 本地模型只读复核。
后续用户提交两题完整回答，后端日志确认新分窗路径成功；这两例本地回归通过，
不代表公开上线、全量评估或所有回答细节已独立核验。

### 问题与证据

用户问 `How should I brew oolong in a mug?`，页面有时提示知识查询失败。
补充阶段日志后发现：Milvus 召回成功，但一个候选的“问题 + 正文 + 特殊 Token”
共 564 Token，超过当前 CrossEncoder 的 512 Token 输入限制，原代码直接抛错，
导致整次知识查询失败。

一次后续请求虽然最终答出，但日志显示 brewing 工具调用仍失败，另一不限制类型的
文章检索成功。这说明“最后有答案”不能证明每个工具都正常；也不能仅据顺序判断模型
是否在看到失败后才决定重试。首次政策查询失败的原始原因未确定，不归因于本次长度问题。

### 根因

切块与向量编码按 BGE-M3 的容量设计，不能保证召回的每段都符合 Reranker 容量。
精排需要把问题和正文一起编码，还要计算成对特殊 Token，不能只检查正文字符数。
原代码的拒绝超长输入保护本身避免了静默丢证据，但缺少可用的长片段处理分支。

### 正式改动

代码：`app/rag/reranker.py`，新增 `_split_long_text()`，调整 `rerank_with_confidence()`。
保持调用方使用的 `[(Document, score), ...], top_score` 返回形式和 `retrieve()` 接口。

1. 短片段仍整体评分，不改变正文与原对象。
2. 超长片段按当前 Reranker tokenizer 切窗口，为问题和成对特殊 Token 预留空间。
3. 使用 fast tokenizer 的 offset_mapping 取得原文位置；窗口正文直接取自原文，
   不通过 decode 重写内容。每个窗口再次成对编码检查，确保真正送入模型的输入不超过512。
4. 所有窗口评分后，每个原候选只保留最高窗口分，避免同一片段占据多个 Top K 名额。
5. 对长片段返回最高分窗口的正文，而非未经该窗口分数验证的全文；复制来源元数据，
   保留 chunk_id，并记录 rerank_window 的原文起止字符位置、原文长度和窗口数。
   原 Document、Milvus 数据和知识库切块都不修改。
6. 增加窗口数量日志；不打印问题、正文或密钥。

项目预算：最多20个候选、每个候选最多8个窗口、总计最多40对输入；
长片段正文窗口最多384 Token，重叠最多64 Token。问题较长时进一步缩小窗口。
这些是当前低频 CPU 服务的保守策略，并非模型要求，也不是评估得到的最优参数。
超过预算明确报错，由既有工具失败路径降级，不悄悄只处理前几个窗口。
这不是硬性的推理中断：Graph 的等待超时仍由现有 wait_for / CPUWorker 处理，
后台 CPU 线程可能继续完成，不能说超时立即释放算力。

### 为什么不直接截取前512 Token

可能把正文尾部的冲泡条件、政策限制或否定信息丢掉，且512还包含问题与特殊 Token。
窗口方案可以在既定预算内给全文各位置评分，并明确返回选中的证据范围。
代价是更多精排计算；不等于全文所有信息都交给了生成模型。

### 验证结果

- 执行 `tests/unit/test_reranker_windows.py`，10项离线回归通过。
  包括512边界、513分窗、尾部证据、原文范围/来源保留、不修改原对象、去窗口重复、
  空结果、异常输出、问题长度、窗口预算、重分词后的真实长度及类别参数传递。
- 使用真实 XLMRobertaTokenizerFast，对226个本地片段和3个固定中英文问题做678次长度检查。
  其中9个成对输入需要分窗，总共生成687个窗口；所有实际窗口输入不超过512 Token，
  原文从开头到结尾均被窗口覆盖。这是分窗正确性检查，不是678道业务问答评估。
- 本机独立 Milvus 19532 + 现有 BGE-M3 + bge-reranker-large 只读复核：

| 查询类别 | 召回候选成对 Token 数 | 结果 | 当次召回及精排总耗时 |
| --- | --- | --- | --- |
| brewing | 559, 498, 494, 487, 528, 410 | 559与528分别切成2窗，6个候选共8窗，返回3条 | 4.146秒 |
| policy | 186, 138, 152, 160, 173, 124 | 全部保持单窗，返回3条 | 1.535秒 |

以上计时不含模型加载和LLM生成，是一次本机运行，不是性能基准或线上延迟承诺。
复核前后 Milvus 都是226条；没有入库、删除、重建、模型下载或付费 LLM 调用。
Tokenizer 检查完整超长输入时会提示超过512，但真正送入 predict 的窗口均在上限内。

### 仍有的限制与后续验收

- 本次 brewing / policy Top-1 精排分数分别约0.0087和0.0196。
  分数不是正确概率，但不能把完成运行等同于检索相关性已达标；后续检查实际证据，
  评估中英文内容与模型的适配情况，不能凭两题设定可靠阈值。
- 最高窗口分是简单聚合策略，长文窗口多时可能更容易出现较高分；未验证优于其他聚合方案。
- 仅返回一个最佳窗口可能缺少其他窗口中的关联条件；重叠不能保证所有完整句子或跨段关系都保留。
- 超出8窗或40对总预算仍会明确失败。当前资料未触发，不声称支持任意长度文本。
- 不解决商品分类/来源范围、原政策失败根因或全部工具效率问题。
- 重启/加载新代码后的两题本地回归已获得用户回答与后端日志支持，见下方追加记录。
  正式网站搜索框验收、更多盲测及故障场景仍未完成。

## 2026-10-21：公开商品咨询被误判为受限请求

### 现象与处理

`Show me your tea pets.` 被本地分类器判为 restricted，服务直接拒答，尚未进入商品查询。
高分类分数不等于判断正确，也不能用商品关键词无条件放行混合敏感请求。

保留现有分类器，仅为 restricted 增加一次不绑定工具的意图复核：
PUBLIC 继续既有 Agent；RESTRICTED 拒答；UNCLEAR 要求重新表述；超时或失败安全降级。
复核最多15秒、16个输出Token、不自动重试；占用原问答模型次数预算，工具白名单不变。
PUBLIC 不是身份验证或后台授权。未重训分类器，也不据此声称分类准确率提升。

涉及 `app/agent/intent_review.py`、`app/agent/service.py`、`app/core/runtime.py`。

### 正式代码复核与证据

- 12项意图复核/服务、10项商品范围/来源、10项精排离线检查全部通过，共32项。
  检查运行时明确绑定到正式模块；外部模型和商品响应使用模拟依赖，不代表线上准确率。
